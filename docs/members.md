# Members, profiles and directory

## Profile ("Mon profil")

- `GET /me`, `PATCH /me`: identity (first name, last name, phone, photo) and FFJDA licence information (birth date, sex, nationality, address, emergency contact). Email change and password change are separate routes, both asking for the current password.
- The photo is uploaded through the storage service (`documents.md`), images only (JPEG, PNG, WebP), 5 MB max, served through `/members/:id/photo`.
- `directory_visible` is toggled here by the member only.
- Photos are cached `private, max-age=300`: after leaving the directory, a photo can stay visible in another member's browser for up to five minutes. Accepted limit.

## Directory ("Annuaire")

- `GET /members?cursor=`: only users with `directory_visible = true`, through a projection carrying first name, last name, photo, phone, email. Never birth date, address, emergency contact, documents, payments.
- The projection is a dedicated `select`, not a filtered object: a field the select does not carry cannot leak.
- Requires a session. Open question: should it require an active membership too? Current choice: any signed-in practitioner, since a trial practitioner needs to reach the instructors.

## Mail

Every mail is sent from `no-reply@joachimjasmin.com` with `Reply-To: info@shobukan-dojo.com` (`MAIL_REPLY_TO`), so a member answering reaches the dojo, and ends with the dojo's signature (address, phone, e-mail, website).

## Admin ("Membres", "Pratiquants")

- `GET /admin/members?cursor=&q=&status=active|past_due|none`: every user, with current subscription (`pickCurrent`, `billing.md`), last paid invoice, failed payments count, last reminder and the validity date of the latest medical certificate (the date only, never the file).
- `GET /admin/members/:id`, `PATCH /admin/members/:id`: every profile field except the password, the role, the email and the directory consent (the latter is the member's own decision).
- `DELETE /admin/members/:id`: erasure through `ErasureService` (`privacy.md`), the only erasure path. An admin cannot erase themself from here (`cannot_delete_self`).
- `POST /admin/members/:id/reminders`: see `billing.md`.
- `GET /admin/members/export`: CSV, UTF-8 with BOM (Excel opens accents correctly), semicolon separator (French Excel). Columns: identity, licence information, subscription status, plan, current licence number. Never the password hash, never medical documents.
- Every export is logged in `member_exports` (who, when, row count) since it takes personal data out of the system.
- Cells starting with `=`, `+`, `-`, `@`, tab or CR are prefixed with `'`: a spreadsheet would otherwise run a member-controlled value as a formula (CSV injection).
- The file is generated by the API and downloaded through the `/api` rewrite with the session cookie.

## Roles

- `PATCH /admin/members/:id/role {role, password}`: the acting admin re-enters their own password (`password_confirmation_failed`), cannot change their own role (`cannot_change_own_role`), and the last admin cannot be demoted (`last_admin`, checked in the same transaction). Every change is journaled in `role_changes` (shown on the member's page) and the member is told by mail.
- The role is re-read on every request: a promotion or a demotion takes effect at once, without touching sessions.
- Throttled to 10 per minute. `admin:grant` on the server remains for the first admin (`deployment.md`).

## Accounts created by an admin

- `POST /admin/members {firstName, lastName, email, phone?, temporaryPassword}` creates a complete account with `must_change_password` and no terms acceptance; pending invitations for that address are revoked. The member gets a mail without the password, which the admin hands over.
- Until the member replaces it, every route but `/auth/me`, `/auth/logout` and `/auth/password` answers 403 `password_change_required`: the admin knows that password. `POST /auth/password` then also requires `acceptTerms` (the account never accepted them), and refuses the same password (`password_unchanged`).
